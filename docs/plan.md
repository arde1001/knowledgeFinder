# Domain-expert RAG demo: project plan

## Context
A student NGO wants a portal tab where members ask a local LLM about the association, events and positions. The tool also answers from the team- or role-restricted Google Drive material that member is allowed to see.
This is a **local proof of concept**: a test filesystem stands in for Google Drive, roles are plain config values, the LLM is a small quantized model on this PC (RTX 2080 Ti, 22 GB; Ollama and llama.cpp are installed, no models pulled yet).
The point is to show that a domain expert can find specific information in a large file structure while **never exposing data the user may not read**. Everything runs as per-component Python CLIs. No web UI in this phase.

The association's real details are sensitive, so everything is synthetic.

## Decisions made with the user
| Topic | Decision |
|---|---|
| Corpus | Synthetic, LLM-generated fake association: md/txt, PDF, docx/xlsx/pptx. About 200-1000 files. Planted fake contact info and "needle" facts. OCR/images are out of scope. |
| Permissions | Roles map to shared drives (member roles), with folder inheritance, individual file/folder shares and org-wide/link-visible items. Modeled on how Google Drive behaves in a typical organisation. A user can hold several roles (union). |
| PII | Simple rule-based stripping (emails, phones, addresses and the like) on text before it reaches the LLM. |
| Stack | Python. One CLI/test harness per component. Ollama with a ~7-14B Q4 instruct model, swappable by config (OpenAI-compatible endpoint where possible). |
| Retrieval | Hybrid. The labeler tree narrows the candidates and embeddings rank within them. |
| Labeler | LLM-written labels, run on demand **by an administrator, never at question time**. It emits a machine-readable filemap plus a human-readable version for verification. |
| Findability | **Only files listed and fully labelled in the filemap are findable.** Unlabelled files on disk are never fed to the expert. |
| Denial | If matches exist only in drives the user cannot read, the expert says matches may exist in Drive X, that the user lacks permission, and whom to ask. It names the drive and its manually labelled contact role only. It never mentions file names, counts, snippets or any other data. |
| Dialogue | Multi-turn chat in the CLI. |
| "Works" means | (1) retrieval hit rate on a Q&A set, (2) automated zero-permission-leak test, (3) automated PII-never-reaches-LLM test, (4) a scripted demo with 2-3 personas that non-technical members can follow. |

## Security invariants (written into the project's CLAUDE.md)
1. The LLM's prompt contains only: system prompt, the user's question and chat history, PII-stripped chunks from files the user may read, and denial notices (drive display name + contact role).
2. Permission is checked in deterministic code, never by the LLM. It is checked **before** any file content is read, and again in the retriever as defense in depth.
3. A denial notice is drive-level only. It carries no file-level data and no count.
4. Chat history stores only final answers. Raw chunks are never persisted across turns. Permissions are re-evaluated every turn.
5. Files absent from the filemap, or only partially labelled, are invisible to the finder and retriever.
6. The labeler and indexer are admin commands. The question path never writes to them.

## Components (build order, each independently testable)
0. **Corpus generator** (`corpus_gen`): creates `testdata/drive/` (shared-drive folders per team), `users.yaml`, `drives.yaml` (drive → member roles, **contact role**, display name), file-level share grants, and an org-wide folder. Also writes ground truth: `qa.jsonl` (question → source files, plus the expected "denied" cases), plus planted PII and needle-fact lists.
1. **Permissions** (`perms`): `can_read(user, path)` implementing roles → drives, inheritance, individual shares and org-wide items. Pure functions with unit tests first. Everything else depends on this.
2. **Labeler** (admin CLI): walks the tree, extracts text (PDF, docx/xlsx/pptx, md), has the local LLM write a short per-file description, and rolls up per-folder labels. It writes `filemap.json` (with content hashes for incremental reruns) and a human-readable `filemap.md`.
3. **Indexer** (admin CLI): chunks and embeds only filemap files. Store is SQLite + numpy brute-force, which is plenty at this scale; upgrade if it grows. Embedding model via Ollama.
4. **Finder**: query (rewritten for multi-turn) → permitted slice of the filemap → LLM or heuristic tree narrowing → embedding rank within the narrowed set → permitted file IDs. In parallel, deterministic code checks the unreadable drives for a likely match and emits `{drive, contact_role}` notices only.
5. **Retriever**: re-checks permission, reads the files, strips PII, returns chunks with source path and drive.
6. **Domain expert**: assembles the prompt, calls the local model, gives a short answer plus sources, and phrases denial notices. Multi-turn history and query rewriting live here.
7. **CLI chat harness**: `login as <user>`, chat, `--debug` to dump the exact LLM prompt (needed for the leak tests).
8. **Eval suite**: hit rate on `qa.jsonl`, the leak test (for every user and every question, scan the captured prompt for any text from unreadable files), the PII test, and the denial-format test.

## Suggested project folder
`~/Projects/<name>/` with `CLAUDE.md` (invariants above, run commands, conventions), `docs/plan.md` (this plan), `src/`, `testdata/`, `evals/`, `pyproject.toml`. Initial CLAUDE.md contents: purpose, security invariants, component list and CLI usage, the "synthetic data only" rule, how to run Ollama and the eval suite.

## Verification (end to end)
- `perms` unit tests cover every Drive behavior listed above, including a file shared to a user whose parent folder is not.
- The eval suite reports retrieval hit rate, zero leaks, zero PII hits and correct denial wording.
- A scripted run of the personas (for example board member, events-team member, plain member) shows different answers and denial behavior to the same questions.

## Settled (second round)
- PII is stripped at retrieval time and on text used for embedding. Originals stay the source of truth.
- Partial access: a user who can read some but not all matches in a drive gets the answer from the readable ones, plus the same drive denial notice. Individual file shares are common, so the notice wording does not change.
- Models: the exact chat and embedding models are chosen by a quick benchmark at the first LLM task.
- Fake association: ~10 teams, ~5 members per team, one general drive everyone can read, random individual file grants scattered over some files.
- Work order: build component by component and **benchmark each one**. Ask when a design is underdefined or a decision needs the user's input.

## Settled (third round): denial trigger and result size
- The finder returns **1-5 readable files** as sources, not just the top one.
- The denial check is deterministic code that compares the query vector with the **chunk vectors** of all labelled files, restricted ones included.
- To keep notices rare (restricted archives such as board-only drives would otherwise win constantly), a notice for drive X fires only when **at least N of the top-K ranked files (ranked over all labelled files) lie in the same restricted drive** and score above a cutoff. N, K and the cutoff are config values, tuned on the eval set with precision/recall reported for notices. Starting guess: K=5, N=2.
- Counting is per drive. The notice text stays identical when the user holds partial access to that drive.
- Only `{drive, contact_role}` leaves the finder. No audit logging in the PoC.

## Confirmed
- "One restricted folder" means one shared drive. The notice is drive-specific and nothing more specific than that.

## Later (not in the demo): scaling and finder ideas
Rough extrapolations from the 530-file run (10k files ~3 h to label, 100k ~1 day on this GPU; 100k files ~2.5M chunks ~8 GB of vectors). Realistic range for the association: 10k-200k text-bearing files.

- **Shard the index by drive.** One vector file per drive, plus a small shard for individually shared files. A session searches only the shards it can access and merges the top results; shards are shared across sessions, so no per-user copies. Helps narrow users most (a member searches their team drives, not everything); the all-access user gains nothing. Until then: one global index and a per-session boolean mask over chunks (drive id and file id per chunk, built from the user's drive set and shared files, cached, rebuilt when permissions change). Keep the restricted-drive comparison for denial notices behind a config switch, so it can be turned off for a stronger isolation guarantee.
- **Cache `live_files`.** About 29 us per file per call is 3 s per query at 100k files. Keep the validated set in memory and refresh on a schedule or from the Drive change feed; index shares by path prefix.
- **Folder labels for big folders.** A folder with more than ~200 files overflows the 8192-token prompt: summarise in batches, then summarise the summaries.
- **Tree-walk on big folders.** Shortlist children by embedding their labels instead of showing them all to the LLM.
- **Real vector index** (FAISS/HNSW, Qdrant or pgvector) above ~1M chunks, with compressed vectors and filtered search; stop holding chunk text in memory.
- **Incremental indexer** (re-embed only new or changed content; today every run rebuilds).
- **OCR** for scanned files; cap text read per file; Drive API export and quotas.
- **Finder quality for the privileged user** (the core goal is less time to find the right file): an all-access persona as the main eval case; headline metric = how many files a user opens before the right one (rank of the correct file); keyword (BM25) signal next to embeddings; recency preference from the label's created date; parse drive/team/event/year from the query as filters; reranking; show path, drive and date with each source; near-duplicate and version handling.
